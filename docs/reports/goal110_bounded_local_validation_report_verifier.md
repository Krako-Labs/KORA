# Goal 110 Bounded Local Validation Report Verifier

Status: implemented with local validation passing and PR open.

## Objective

Goal 110 adds a small public-safe verifier for JSON reports generated by the Goal 109 bounded local validation runner.

The verifier reads a report file, validates its structure, checks the approved `kora-local-core` profile and command list, and exits nonzero for malformed or unsupported reports. It does not execute commands from the report.

## Verifier CLI Usage

```bash
python3 scripts/verify_bounded_local_validation_report.py \
  /tmp/kora-goal109-bounded-local-validation.json \
  --profile kora-local-core
```

Failed reports are rejected by default:

```bash
python3 scripts/verify_bounded_local_validation_report.py report.json --profile kora-local-core
```

Structurally valid failed reports can be accepted for triage with:

```bash
python3 scripts/verify_bounded_local_validation_report.py report.json --profile kora-local-core --allow-failed
```

## JSON Report Contract

The verifier expects a JSON object with:

- `profile`
- `final_status`
- `repo_root` or `repository_root`
- `steps`

The runner now also writes:

- `report_schema`: `kora.bounded_local_validation.v1`

The verifier accepts the Goal 109 report shape and checks `report_schema` when present. Each step must include:

- `name`
- `command` or `argv`
- `status`
- `return_code`, `returnCode`, or `returncode`

Accepted step statuses:

- `passed`
- `failed`
- `skipped/dry-run`

## Supported Profile

The only supported profile is `kora-local-core`.

The approved command list is:

```bash
python3 scripts/evaluate_fixture_quality_checks.py
python3 -m pytest tests/test_fixture_quality_checks.py
python3 -m pytest tests/test_representativeness_seed.py tests/test_representativeness_route_only_evaluator.py
python3 scripts/check_markdown_links_goal082b.py
git diff --check
python3 -m pytest
```

Reports with unknown profiles, arbitrary profile names, missing fields, invalid statuses, malformed JSON, or mismatched command lists fail verification.

Passed and dry-run reports must include the full approved command list. Failed reports may include the approved command prefix that the Goal 109 runner records before stopping at the first failed step.

## Failed And Dry-Run Behavior

Failed reports are structurally valid if their fields and approved command list match the contract, but they return nonzero unless `--allow-failed` is supplied.

Dry-run reports are structurally valid when all steps are marked `skipped/dry-run`.

## Safety Boundaries

Goal 110 keeps the verifier within these boundaries:

- no arbitrary shell command execution.
- no execution of commands from the report.
- no auto-repair.
- no scheduler.
- no daemon.
- no background runner.
- no GitHub Actions workflow.
- no remote runner.
- no provider-calling runner.
- no H100 runner.
- no self-merging agent.
- no provider calls.
- no H100/GPU/CUDA/server/remote execution.
- no model inference.
- no semantic judging.
- no human grading.
- no production validation.
- no file movement.
- no local-only ChatGPT context changes.
- no releases, tags, release assets, GitHub issues, project boards, repository settings, or collaborator changes.

## Claim Boundaries

Goal 110 does not claim:

- output-quality proof.
- broader workload representativeness proof.
- production proof.
- production cost reduction.
- customer savings.
- H100/GPU/CPU superiority.
- provider replacement or GPU-serving replacement.
- that `getkora` is published.

The verifier checks local runner report structure only. It is not production validation, output-quality proof, or broader workload representativeness proof.
