# Goal 110 Bounded Local Validation Report Verifier

Status: implemented with local validation passing before PR open.

## Objective

Goal 110 adds a small public-safe verifier for JSON reports generated by the Goal 109 bounded local validation runner.

The verifier checks report structure and the approved `kora-local-core` command list. It does not execute commands from reports and is not production validation, output-quality proof, broader workload representativeness proof, or production proof.

## Verifier CLI Usage

Verify a Goal 109 JSON report:

```bash
python3 scripts/verify_bounded_local_validation_report.py \
  /tmp/kora-goal109-bounded-local-validation.json \
  --profile kora-local-core
```

Accept a structurally valid failed report:

```bash
python3 scripts/verify_bounded_local_validation_report.py \
  /tmp/kora-goal109-bounded-local-validation.json \
  --profile kora-local-core \
  --allow-failed
```

## JSON Report Contract

The verifier expects a JSON object with:

- `profile`
- `final_status`
- `repo_root` or `repository_root`
- `steps`

The optional schema field is `report_schema: kora.bounded_local_validation.v1`. Reports without the schema field remain accepted for simple backward compatibility.

Each step must contain:

- `name`
- `command` or `argv`
- `status`
- `return_code` or `returnCode`

Allowed statuses are:

- `passed`
- `failed`
- `skipped/dry-run`

## Supported Profile

The only supported profile is `kora-local-core`.

Unknown or arbitrary profiles fail with a nonzero exit code. The verifier reads report data only and does not execute any command from the report.

## Approved Command List

The `kora-local-core` report must contain exactly these commands, in this order:

```bash
python3 scripts/evaluate_fixture_quality_checks.py
python3 -m pytest tests/test_fixture_quality_checks.py
python3 -m pytest tests/test_representativeness_seed.py tests/test_representativeness_route_only_evaluator.py
python3 scripts/check_markdown_links_goal082b.py
git diff --check
python3 -m pytest
```

## Failed Report Behavior

Failed reports are structurally valid if the fields and commands match, but the verifier returns nonzero by default when `final_status` is `failed` or any step status is `failed`.

Use `--allow-failed` to accept failed reports for structure-only review.

## Dry-Run Report Behavior

Dry-run reports are structurally valid when all steps are marked `skipped/dry-run` and the approved command list is present.
