# KORA Solution SDK and Conformance Kit v0alpha1

Status: bounded deterministic authoring and local conformance foundation.

This foundation helps maintainers create and check KORA Solution Protocol packages without provider calls, model inference, network access, GPU execution, or workflow-specific KORA Core changes. It is an alpha developer path, not a package-signing, distribution, production-sandbox, or marketplace claim.

## Scaffold a Solution

Create a new package in a path that does not already exist:

```bash
python3 -m kora solution scaffold example.my-solution --output ./my-solution --json
```

The scaffold emits:

```text
my-solution/
  solution.json
  README.md
  graph/
    workflow.json
  schemas/
    input.schema.json
    output.schema.json
  examples/
    input.json
  conformance/
    cases/
      echo-success.json
```

The initial template is intentionally narrow. It uses the existing `det.echo` capability, declares `network: denied`, has no side effects or approvals, and uses JSON Schema Draft 2020-12 for input and output.

For the same Solution id and version, scaffolded file bytes and the reported package digest are deterministic. The command refuses to overwrite an existing path. The generated manifest binds every non-manifest file to a SHA-256 digest; `solution.json` remains outside its own integrity map to avoid a circular self-digest.

The Python authoring surface also exports:

- `scaffold_solution`;
- `integrity_file_digests`;
- `package_file_digests`;
- `package_digest`;
- `SolutionAuthoringError`.

These helpers reject symbolic links and non-regular package entries. Archive creation, signing, publication, YAML conversion, and arbitrary templates are deferred.

## Declare conformance cases

A package checked with the Conformance Kit contains one or more regular JSON files under `conformance/cases/`. Every case file must be listed in `solution.json` under `integrity.files`.

Each case declares:

- `schema_version`;
- a stable `case_id`;
- object input;
- explicit approval grants;
- expected final lifecycle state;
- expected input/output validation states;
- expected object output or bounded error code;
- expected executed capabilities;
- expected lifecycle history.

The machine-readable contract is bundled as `kora/solution/schemas/conformance-case.schema.json`.

Cases may declare expected successful or expected failed runs. For example, an invalid-input case can conform when it expects `input_validation_failed`, no execution, and the verified `created -> validating -> failed` transition. A failed expectation is a conformance failure; it is not rewritten into a passing result.

## Run conformance

Run the package-declared suite:

```bash
python3 -m kora solution conform ./my-solution --json
```

The runner:

1. creates a fresh temporary local Host store;
2. validates package integrity and resolves the local reference runtime;
3. validates integrity-bound conformance case contracts;
4. computes the complete package-tree digest;
5. installs and revalidates the package in the isolated store;
6. runs cases in filename order with their explicit approval grants;
7. retrieves and schema-validates each persisted status and result;
8. compares identity, lifecycle, validation, output/error, capabilities, history, and evidence references;
9. verifies that network, model, and GPU activity facts remain false;
10. emits a schema-validated report.

A conforming report exits with status 0. A valid report containing expectation failures exits with status 1 on the CLI and is written to standard output. Setup, package, integrity, or case-contract failures exit with status 1 and a bounded machine-readable error on standard error.

The report contract is bundled as `kora/solution/schemas/conformance-report.schema.json`. It includes the Solution Protocol version, package identity and digest, selected runtime identity and descriptor digest, per-case checks and run references, aggregate counts, activity facts, and timestamps.

The temporary Host store is removed after the report is assembled. Run references identify the status and result records that were schema-validated during the check; they are not durable evidence archives.

The Python conformance surface exports:

- `run_solution_conformance`;
- `SolutionConformanceError`;
- `CONFORMANCE_CASE_SCHEMA`;
- `CONFORMANCE_REPORT_SCHEMA`.

## Reference coverage

The same entry point checks:

- `examples/solutions/hello-solution`;
- `examples/solutions/document-transform-fixture`;
- `examples/solutions/generated-echo-fixture`, which is generated by the scaffold command.

Automated coverage includes deterministic scaffold reproduction, existing-path refusal, schema-invalid cases, non-integrity-bound cases, invalid input, invalid output, missing capability, undeclared side effect, package tampering, expected failure cases, lifecycle history, persisted contracts, and zero network/model/GPU activity.

## Current boundary

Implemented:

- one deterministic JSON scaffold template;
- fail-closed path and overwrite handling;
- complete package-tree digest helpers;
- integrity-bound conformance cases;
- isolated validate/install/run/status/result execution;
- machine-readable case and report schemas;
- deterministic positive and negative test fixtures.

Deferred:

- arbitrary templates or interactive generators;
- package archives, signing, trust roots, publication, and updates;
- dynamic or remote runtime loading;
- Registry or marketplace behavior;
- stop/resume and checkpoints;
- cache execution;
- provider, model, network, and GPU capabilities;
- production validation;
- commercial Solution selection.

Passing this kit demonstrates only the bounded protocol behavior checked by its declared cases. It does not establish production readiness, output quality, security certification, customer savings, or broader workload performance.
